## S0-000 Review

### Strengths
- Excellent awareness that "explicit" in CONTRACT.md means concrete numeric values, not qualitative prose. Decision 2 (Option A: concrete numeric values) is the right call and well-justified.
- The wrong-implementation analysis (section 5) is unusually thorough for a doc-only story. The "instruments: see exchange documentation for current list" wrong impl is sharp -- it targets the exact kind of lazy compliance that a weak implementer would attempt.
- Assumption 6 (P0-F format compatibility) correctly identifies the primary interface risk: this document is consumed downstream, and format mismatches will compound.
- The "byte-for-byte identical" decision for snapshots is clean and eliminates ambiguity.

### Gaps Found
- **Assumption 3 (literal copy) is listed as "Not formally tested" but should be trivially automatable.** A `diff` check is mentioned repeatedly as something that "could be" automated but is not. Given that this is a one-line shell command, the decision to defer it feels like artificial scope reduction. If the premortem knows the gap and knows the fix, why defer?
- **No assumption about the relationship between S0-000's values and S0-005's (P0-F) schema.** Assumption 6 mentions "format/structure must be compatible" but does not identify the specific risk: if S0-000 uses Markdown table format with inconsistent column names or units, S0-005 may silently parse wrong values. The assumption should specify an interface contract (e.g., "position limits are in base currency units, not quote").
- **Missing assumption: Are the constraint values correct?** All assumptions focus on document structure and completeness, but none addresses the risk that a well-formatted document with numerically incorrect limits (e.g., max position 100 BTC instead of 0.1 BTC) passes all structural checks. This is arguably the highest-risk failure for a policy document.

### Missing Failure Modes
1. **Copy-paste unit error.** The document specifies "max position: 0.1" but omits the unit (BTC? USD? contracts?). P0-F's loader interprets the number with a different unit assumption. This is distinct from FM-5 (prose-only) because the value IS numeric but the unit is wrong or absent.
2. **Constraint values are correct for one instrument but wrong for another.** The policy lists a single set of limits but the instrument list includes assets with vastly different characteristics (e.g., BTC and a low-liquidity altcoin). A 0.1 position limit is conservative for BTC but could be large for an illiquid instrument. The policy should indicate whether limits are per-instrument or global.
3. **Document merged without review.** The premortem assumes a review gate exists, but if the document is merged via a fast-track process (e.g., during a late-night push), the review-based acceptance criteria provide zero protection.

### Missing Wrong Implementations
- **Wrong impl: document is generated by copying a template and filling in values from a different exchange/account.** The values look plausible (they are numeric, complete, and well-structured) but do not reflect the actual exchange's constraints (e.g., the exchange's minimum order size is 0.001 BTC but the policy says 0.01, or the exchange does not support one of the listed instruments). This wrong impl passes every structural check and even looks reasonable to a reviewer without exchange-specific knowledge.

### Stoplight Assessment
YELLOW is honest. The story is genuinely low-risk, and the debt register items have owners and target slices. The only concern is that 3 of 4 debt items point to "P0-F (S0-005)" as the target slice, which concentrates the repayment burden. If S0-005 is already complex, these deferred items may be dropped.

### Verdict: ACCEPT

The premortem is thorough for a documentation story. The gaps identified above are real but do not change the risk profile. The missing failure modes (unit errors, per-instrument applicability) should be noted in the debt register for the S0-005 premortem to pick up.

## S0-001 Review

### Strengths
- Assumption 4 (key permissions actually enforced at the exchange level) is sharp -- it correctly identifies that documentation can claim isolation that does not exist in reality.
- Assumption 5 (secrets not in git) with the concrete `git log --all -p` verification command is actionable and testable.
- The boundary with P0-C is clearly drawn: S0-001 documents WHAT exists; P0-C documents HOW keys are managed. This prevents scope creep.
- Failure mode 2 (aspirational documentation -- "claims separate accounts but reality is shared") targets the most dangerous failure: a false sense of isolation.

### Gaps Found
- **The premortem does not address what happens if environments share infrastructure beyond accounts.** Separate exchange accounts are necessary but not sufficient for isolation. If DEV and LIVE share the same server, network, or deployment pipeline, an environment misconfiguration can still cause cross-contamination. The env matrix should document infrastructure separation, not just account separation.
- **Decision 1 (secrets storage granularity) chooses Option A (storage system only) but this conflicts with S0-002's scope.** S0-002 (P0-C) is supposed to document "where secrets live" in detail, but S0-001 also has an acceptance criterion about where secrets are stored. If S0-001 says "1Password" and S0-002 says "AWS Secrets Manager," the documents contradict each other. The premortem notes the P0-C boundary but does not define an explicit reconciliation mechanism.
- **No assumption about the completeness of the environment list itself.** The premortem assumes DEV/STAGING/PAPER/LIVE are the four environments, but what if additional environments exist (e.g., CI, LOAD-TEST, CANARY)? The env matrix would be incomplete. Assumption 1 touches on naming but not on whether the list is exhaustive.

### Missing Failure Modes
1. **Environment matrix is correct at creation time but infrastructure changes are not reflected.** This is distinct from FM-5 (snapshot staleness) -- the canonical doc itself becomes stale because the infrastructure evolves but the doc is not updated. There is no trigger or process to update `docs/env_matrix.md` when a new environment is provisioned or an account is changed.
2. **LIVE row has real account IDs or sensitive identifiers.** The env matrix is committed to git. If it includes real exchange account IDs, API key prefixes, or server hostnames, it becomes a reconnaissance target for an attacker. The premortem does not consider information leakage via the documentation itself.

### Missing Wrong Implementations
- **Wrong impl: env matrix uses generic/template account names ("acct-dev-001", "acct-staging-001") that look concrete but are not the real account identifiers.** The matrix appears complete and specific but is actually fictional. Only someone with exchange admin access could verify, and the reviewer may not have that access.

### Stoplight Assessment
YELLOW is honest. The debt items are tracked with target slices. The three debt items are reasonable deferrals. However, the "Acceptance criteria accept vacuous docs" debt item has target "PRD amendment" which is vague -- when does the PRD get amended? By whom? This should have a concrete target slice or story ID.

### Verdict: ACCEPT

The premortem is solid. The information-leakage gap (real account IDs in git-committed docs) should be explicitly addressed, and the P0-C boundary needs a reconciliation note to prevent contradictions.

## S0-002 Review

### Strengths
- The risk rating upgrade from LOW to LOW-to-MED is well-justified and shows independent thinking. The premortem correctly identifies that a key scope probe is not just documentation -- it is evidence of a security property, and false evidence is worse than no evidence.
- Failure mode 1 (hand-crafted JSON claiming false privilege) is the single most important adversarial scenario for this story. The premortem identifies it clearly and proposes the right mitigation: the transfer rejection test should attempt a real transfer, not just check a field.
- The CLAIMED-NOT-PROVEN analysis in section 6 is excellent -- explicitly calling out that the implementation tests exist in a "traceability vacuum" with no contract AT binding.
- Wrong implementation analysis for the "scopes: [all]" case is precise and catches a real gap in field-value (vs. field-presence) checking.

### Gaps Found
- **Decision 2 chooses Option B (tests validate static JSON, not live API) but then acknowledges this means the probe can be fabricated.** This creates a circular argument: the premortem identifies the risk (hand-crafted JSON), notes the mitigation (tests should hit real API), and then predicts the tests do NOT hit real API. The result is that failure mode 1 has no mitigation. The premortem acknowledges this but does not escalate it in the stoplight. This gap should arguably make the probe-related items MED severity in the debt register, not LOW.
- **Assumption 2 (probe generated from actual API call) is marked "Blind -- depends on test implementation" but should be flagged as a hard requirement, not just an assumption.** If the probe is hand-crafted, the entire "least-privilege proof" claim in P0-C is fraudulent documentation. This is not a "Low" severity debt item -- it undermines the contract clause's intent.
- **No assumption about key rotation invalidating the probe.** If a key is rotated after the probe is captured, the probe evidence refers to a now-revoked key. The new key's permissions are unknown. The probe should include the key creation timestamp or a mechanism to detect probe staleness relative to key age.

### Missing Failure Modes
1. **Exchange changes scope model.** The exchange updates its API key permission system (e.g., renames "withdraw" to "transfer_out", adds new permission types). The probe checks for `withdraw_enabled: false` but the dangerous permission is now called something else. The allowlist-based scope check becomes stale.
2. **Probe is from PAPER environment but is used to justify LIVE key safety.** The `env` field distinguishes environments, but if only a PAPER probe is produced and the LIVE key is configured differently, the evidence does not cover LIVE. Failure mode 4 touches on this but frames it as "testnet vs LIVE divergence" -- the sharper framing is: the contract says "least-privilege proof" with no qualifier that it is per-environment, so a reviewer might accept a PAPER-only probe as sufficient for the entire P0-C claim.
3. **The `operator` field in the probe is self-reported.** The probe JSON includes an `operator` field, but nothing prevents the operator from falsifying it. If the point is accountability, a self-reported operator field is theater unless it is cross-referenced with commit authorship or a signed attestation.

### Missing Wrong Implementations
- **Wrong impl: tests validate that `withdraw_enabled == false` but the exchange does not use boolean for this field -- it uses a scopes array.** The test checks the wrong field type or path in the JSON, passes because the field is absent (and absence defaults to false), but the actual key permissions are not what the probe claims. This is a data-model mismatch between the probe schema and the exchange's actual API response format.
- **Wrong impl: tests import the probe JSON and validate it, but the probe JSON checked into evidence/ is a different file from the one actually generated by the API call.** The implementer runs the API probe, gets results they do not like, hand-edits the JSON, and commits the edited version. Tests validate the committed file, not the API output.

### Stoplight Assessment
YELLOW is arguably too generous. The premortem itself identifies that:
1. The probe can be fabricated (FM-1)
2. The tests likely validate static JSON, not live API (Decision 2, Option B)
3. The implementation tests have no contract AT binding

Combined, these mean the "least-privilege proof" in P0-C could be entirely fictional and no automated system would catch it. For a story dealing with API key security boundaries, this is a meaningful gap. I would argue this should be YELLOW-HIGH or borderline RED, with the probe-provenance item elevated to MED severity.

However, given that this is Phase 0 and the practical risk is bounded by the fact that LIVE trading does not happen until later phases (and P0-F/Kill mode provide runtime backstops), YELLOW is defensible if the debt items are taken seriously.

### Verdict: ACCEPT with reservations

The premortem is analytically strong but slightly too forgiving in its stoplight assessment. The probe-provenance debt item should be elevated to MED severity, and the circular reasoning in Decision 2 (predicting Option B while identifying that Option B leaves FM-1 unmitigated) should be explicitly flagged as a tension that the reviewer must resolve during implementation review.

## S0-003 Review

### Strengths
- **Risk rating upgrade from LOW to HIGH is the right call and well-argued.** The reasoning is precise: this is the last-resort safety mechanism, and a false-confidence runbook is worse than no runbook. The sentence "a break-glass runbook that does not actually halt trading creates false confidence in the most critical safety escape hatch" is exactly right.
- Failure mode 3 (missing "cancel outstanding OPENs" step) is sharp and targets a real gap between Kill semantics (no NEW exposure) and in-flight order management. Kill blocks new dispatches but does not recall orders already on the exchange. This is a genuinely non-obvious failure mode.
- Assumption 6 (verify step checks for inflight/queued orders, not just TradingMode state) is excellent -- it identifies the gap between "system state says Kill" and "exchange state has no open orders."
- The wrong-impl analysis is the strongest of all four premortems. Eight acceptance criteria analyzed, each with a specific wrong-impl that targets the exact kind of "theater compliance" a lazy implementer would produce.
- The economic risk analysis is clear-eyed: "The break-glass itself IS the fail-closed cap."

### Gaps Found
- **Decision 2 (trigger mechanism) is unresolved.** The premortem says "Cannot decide blindly" and defers it to the debt register. This is honest, but the premortem should still rank the options by safety properties. File sentinel (Option A) is the most fail-safe because it survives process hangs (the filesystem is external to the process), while API (Option B) fails when the process is unresponsive and signal (Option C) fails if you do not know the PID. The premortem should have stated a preferred option even while acknowledging it cannot verify.
- **No assumption about network partitions.** The runbook assumes the operator can reach the server and the exchange. What if the emergency is caused by a network partition? The break-glass procedure should have a "if you cannot reach the system" fallback (e.g., "log into the exchange directly and disable the API key"). This is not just an edge case -- network issues are a common trigger for trading emergencies.
- **Failure mode 2 (paper-only drill) mitigation is weak.** The detection is "log excerpt must have timestamps and Kill-mode transition entries that are internally consistent," but an implementer who fabricates logs will also make them internally consistent. The real mitigation should be requiring the drill to produce artifacts that are independently verifiable (e.g., git commit timestamps, CI job IDs, exchange API audit logs).
- **No assumption or failure mode about partial Kill.** What if Kill mode is correctly set for the primary trading loop but a secondary component (e.g., a reconnection handler, a position sync job) continues to create exposure? The runbook says "set Kill" but does not address whether Kill propagates to all subsystems. This is a system-level failure mode that the per-component tests would not catch.

### Missing Failure Modes
1. **Runbook tested in DEV, fails in PROD due to different deployment topology.** The command path works on a single-process dev machine but production has multiple processes, containers, or a load balancer in front. The file sentinel path is different, or the process PID namespace is different. The drill passes against the dev environment but the runbook is not portable.
2. **Operator triggers Kill but does not verify it took effect.** The runbook says "trigger Kill" and the operator does so, but a bug prevents the mode transition (e.g., the file sentinel is not on the right path, or the watcher is not running). The operator assumes Kill is active and walks away, but trading continues. The runbook must include a mandatory verification step with specific expected output.
3. **Race condition between Kill trigger and in-flight dispatch.** The operator triggers Kill, but at the exact moment of the trigger, an OPEN intent is in the process of being dispatched (past the PolicyGuard check but not yet sent to the exchange). The Kill takes effect after the dispatch call is already in-flight. The premortem's failure mode 3 (cancel outstanding OPENs) partially covers this, but the race between trigger and in-flight dispatch is a distinct timing hazard.

### Missing Wrong Implementations
- **Wrong impl: drill.md documents a drill that happened, but the drill used a different version of the runbook than what is committed.** The drill evidence says "we followed the runbook" but the runbook was edited after the drill. The evidence no longer matches the current document. This is the "snapshot staleness" problem applied to the drill evidence.
- **Wrong impl: log_excerpt.txt is from a real Kill mode activation, but it was an ACCIDENTAL Kill (not a drill).** The logs are authentic but the "drill" was actually an unplanned incident. There was no deliberate trigger-observe-verify cycle; the system just happened to enter Kill at some point. This satisfies "log_excerpt proves drill occurred" by redefining "drill" as "any Kill event."

### Stoplight Assessment
YELLOW is arguably too lenient given the premortem's own risk rating of HIGH. The premortem upgrades the risk to HIGH (the last-resort safety mechanism) but then gives it the same YELLOW stoplight as the LOW-risk documentation stories (S0-000, S0-001). If the break-glass runbook is the "most critical safety escape hatch" and all 8 acceptance criteria are subjective document reviews with no automated enforcement, the stoplight should be at least YELLOW-HIGH with a stronger signal that the drill evidence quality is a hard gate at review time.

The debt register items are reasonable, but the "All 8 acceptance criteria are document-review only" item is listed as MED severity. For a HIGH-risk story where the acceptance mechanism is entirely human judgment, this feels understated. What is the plan if the reviewer is under time pressure and rubber-stamps the review?

### Verdict: ACCEPT with reservations

The premortem is the strongest of the four -- analytically sharp, adversarially minded, and honest about the blind spots. The gaps are about missing environmental failure modes (network partitions, deployment topology differences, partial Kill propagation) that are hard to anticipate in a premortem. The stoplight should be upgraded to reflect the HIGH risk rating, or the risk rating should be downgraded to match the YELLOW stoplight -- they are currently inconsistent.

## Cross-Story Findings

### 1. Shared blind spot: snapshot staleness across all four stories

All four premortems identify "evidence snapshot diverges from canonical doc" as a failure mode (S0-000 FM-2, S0-001 FM-5, S0-002 implicitly via probe provenance, S0-003 via drill evidence). All four defer automated diff/freshness checks. This is the same gap repeated four times with no story owning the fix. If a CI freshness gate is going to be built, it should be a single cross-cutting story, not deferred debt in four separate debt registers pointing at vague "future" targets. **Recommendation:** Create a single "evidence freshness CI gate" story that covers all Phase 0 evidence files, rather than deferring independently in each premortem.

### 2. Contradiction: S0-001 and S0-002 overlap on "where secrets are stored"

S0-001 (env matrix) has acceptance criterion "shows where secrets are stored" and S0-002 (keys & secrets) is entirely about key management including secret storage. If S0-001 says secrets are in "1Password" and S0-002 says "AWS Secrets Manager" (or gives more granular detail that implies a different system), the two documents contradict each other. Neither premortem defines which document is authoritative for secret storage location. **Recommendation:** One of the two premortems should define S0-001's "where secrets are stored" as a summary reference to the S0-002 document, not an independent claim.

### 3. Contradiction: S0-003 rates itself HIGH but gets YELLOW stoplight; S0-000/S0-001 rate themselves LOW and also get YELLOW

The stoplight system loses its signaling power if a HIGH-risk story and a LOW-risk story both get YELLOW. The stoplight should reflect the combination of (risk severity) x (gap severity). S0-003's YELLOW should be a harder YELLOW or a soft RED given that the entire acceptance mechanism is subjective for a safety-critical escape hatch. Alternatively, S0-000 and S0-001 could arguably be GREEN (their gaps are genuinely minor for documentation stories with no runtime impact).

### 4. All four stories share the same structural weakness: no formal ATs

Every premortem says "enforcing_contract_ats: []" and handles this with "N/A" or "analyzed against acceptance criteria instead." This is four stories in a row with zero automated enforcement. Phase 0 is by definition an operational-prerequisites phase, so this may be by design. But the pattern means that ALL of Phase 0 can be "passed" by a reviewer who rubber-stamps, with no CI backstop. The premortems individually note this as debt, but collectively it represents a systemic gap: Phase 0 has no automated quality gate whatsoever. **Recommendation:** Even one simple CI check (file existence + `diff` for snapshots + basic structure grep) across all P0 evidence files would dramatically reduce the rubber-stamp risk.

### 5. P0-F (S0-005) as a debt sink

S0-000 defers 3 of 4 debt items to S0-005 (P0-F Machine Policy Loader). S0-001 defers 1 item to S0-005 territory. S0-002 defers probe-schema validation to a similar "future" target. If S0-005's premortem does not explicitly pick up these deferred items, they will be silently dropped. There is no mechanism to ensure that debt deferred to a target slice is actually addressed by that slice. **Recommendation:** The S0-005 premortem should include a "debt intake" section that explicitly lists and addresses all items deferred to it by earlier stories.

### 6. S0-003 depends on Kill mode correctness that S0-000/S0-001/S0-002 cannot verify

S0-003's break-glass procedure depends on Kill mode dispatch authorization (section 2.2.3.4, section 2.2.3.6), but none of the earlier stories touch runtime code. If the Kill mode implementation has a bug, S0-003's drill might pass (in a test harness with correct Kill behavior) while production has a different code path. This is not a contradiction between premortems but an interaction gap: S0-003's safety depends on code that is not in S0-003's touch scope, and no earlier S0 story validates that code. The implementation tests (`test_break_glass_kill_blocks_open_allows_reduce_runtime`) are the only bridge, but they exist in the soldier_infra test file -- if that file has issues, S0-003's safety claim collapses.

### 7. Information flow: S0-000 -> S0-005, S0-001 -> S0-002, S0-003 -> runtime Kill

The four stories form an implicit dependency chain, but the premortems do not define interface contracts between them. Specifically:
- S0-000 produces values that S0-005 must consume. Neither defines the interface format.
- S0-001 documents secrets location that S0-002 also documents. Neither defines which is authoritative.
- S0-003 documents a procedure that depends on runtime code from a completely different crate. The premortem acknowledges this but cannot verify alignment.

These are interface risks that no single premortem owns. A cross-story integration check -- even a simple "do the documents agree with each other" review -- would catch inconsistencies before they compound.
