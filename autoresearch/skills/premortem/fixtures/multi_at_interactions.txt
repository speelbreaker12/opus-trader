Story: S6-002 — Position limit enforcement with reservation awareness
Risk Rating: HIGH
Contract: specs/CONTRACT.md §2.3 (Position Limits and Risk Boundaries)
Acceptance Tests: AT-070 (ReservationGate blocks OPEN when pending reservations + position exceed limit), AT-071 (ExposureGate rejects when net exposure exceeds threshold), AT-072 (PositionLimitGate rejects OPEN when position count at max)
Enforcement Point: DispatcherChokepoint — build_order_intent.rs (three gates in sequence)
Touch Scope: crates/soldier_core/src/execution/build_order_intent.rs, crates/soldier_core/src/execution/reservation_gate.rs (new), crates/soldier_core/src/execution/exposure_gate.rs (modified), crates/soldier_core/src/execution/position_limit_gate.rs (modified)

Description:
This story modifies three interacting gates in the execution pipeline to enforce position limits
with reservation awareness. Currently:
- ExposureGate checks net dollar exposure but ignores pending reservations
- PositionLimitGate checks instrument count but ignores pending reservations
- No ReservationGate exists

The new design:
1. ReservationGate (new): Before checking position limits, account for all pending order
   reservations. A reservation is created when an intent passes all gates and is dispatched
   but not yet filled/cancelled. The gate adds pending reservation quantities to the current
   position before limit checks.

2. ExposureGate (modified): Now receives reservation-adjusted exposure instead of raw exposure.
   The gate must reject OPEN intents when reservation-adjusted net exposure exceeds the
   per-instrument threshold.

3. PositionLimitGate (modified): Now receives reservation-adjusted position count. The gate
   must reject OPEN intents when reservation-adjusted count reaches the max.

Key interactions:
- AT-070 and AT-072 share the reservation state — if reservation tracking is wrong, BOTH gates
  produce incorrect results
- AT-071 depends on AT-070's reservation adjustment being applied BEFORE exposure calculation
- If reservations are double-counted (race between fill confirmation and new intent), all three
  gates become overly restrictive (fail-closed but blocks valid profit)
- If reservations are under-counted (stale fill not cleared), all three gates become permissive
  (fail-OPEN risk — the dangerous case)
- The ordering matters: ReservationGate must run before ExposureGate and PositionLimitGate

Pipeline ordering after change:
  RiskState → Preflight → Quantize → NetEdge → Pricer → ReservationGate → ExposureGate → PositionLimitGate → LiquidityGate → RecordedBeforeDispatch → Dispatch

Prior postmortem: artifacts/story/S6-001/postmortem.md
- Section 8 startup note: "Reservation state is shared mutable — any new gate reading it must
  handle stale/missing reservation entries as fail-closed (over-count, not under-count)"
