Story: S3-015 — Add cached trading mode for fast-path dispatch
Risk Rating: HIGH
Contract: specs/CONTRACT.md §2.2 (PolicyGuard TradingMode Resolution)
Acceptance Tests: AT-030 (PolicyGuard resolves ReduceOnly when policy is stale), AT-031 (PolicyGuard resolves Active only when all checks pass)
Enforcement Point: PolicyGuard — policy/guard.rs
Touch Scope: crates/soldier_core/src/policy/guard.rs

Description:
This story adds a caching layer to PolicyGuard's trading mode resolution. The current
implementation re-evaluates all policy inputs on every tick, which is expensive. The proposed
design caches the last resolved mode and returns it on subsequent ticks until invalidated.

Proposed implementation:
```rust
pub fn resolve_trading_mode(&self, ctx: &TickContext) -> TradingMode {
    // Fast path: return cached mode if recent
    if let Some(cached) = self.cached_mode {
        if self.cache_age() < Duration::from_millis(100) {
            return cached;
        }
    }
    // Slow path: re-evaluate all inputs
    // ... existing logic ...
}
```

The designer proposes that when the cache is empty (first tick or after restart), the default
should be `TradingMode::Active` to avoid blocking the first trade:

```rust
let mode = self.cached_mode.unwrap_or(TradingMode::Active);
```

Rationale given: "We don't want to miss the first trading opportunity after restart. The cache
will be populated within 100ms."

This design has a known anti-pattern: using `unwrap_or(TradingMode::Active)` as a default
violates the fail-closed principle. If the cache is empty, stale, or corrupted, the system
should default to ReduceOnly (the safe state), not Active (the permissive state).
